# V9 压力完成损失：原档与离线诊断

本报告分析 V9 首次冻结实验中相对 V7/V8 的压力面板完成损失。它是**看过结果后的开发诊断，不是新的留出验证**。原方法、200 ms 日预算、5 秒冷启动 episode、随机种子和首次结果均未修改，也未重新运行在线策略。

结论是：三个失败 episode 都存在当前观察与原物理前缀下的可行计划。两次 D3 失败的 MILP 响应在外层 200 ms 截止后才到达，且原档没有保存其迟到日期；一次 D7 失败保存了完整且可独立复核的有效计划，但最终选择在 200.039 ms 才完成。因此，不能将它们解释为当前观察下的资源数学无解，也不能把离线找到计划等同于原策略已经能及时完成。

## 证据与范围

- 机器可读产物：[v9-loss-diagnosis.json](../data/v9-loss-diagnosis.json)，464,054 字节。
- 诊断实现：[diagnose-v9-losses.py](../scripts/diagnose-v9-losses.py)。
- V9 首次正式索引 SHA-256：`83d165a965e421af0ebc0b399f426eab3ae48eddc4a564374a6074f9edad7204`。
- 完整报告逐一绑定发布索引、冻结 manifest、输入及 V7/V8/V9 episode 的原文件 SHA；冻结实现中的 gate、构造器、MILP、原生服务及独立审计源码另列 SHA。
- 当前公开快照由独立 Python ledger 重建，核对原 observationHash；物理锁仅从失败日前实际执行的事件重建。
- 四个比较损失去重为三个失败 episode；没有把同一个 a3 失败重复计为两次独立失败。
- 不使用全知实际未来容量作为诊断求解输入。没有新增或替换业务场景。

这里的“a2/a3”分别指同一业务场景的第 2/3 次算法与时钟重复，算法种子为 39023/39039，不是新的独立业务样本。

## 逐例原始机制

| 失败 episode（省略共同前缀 `v9-stress-`） | 损失相对谁 | 失败日 | 原物理锁 | 原缓存当日运输 / 已知容量 | 原始外层 gate 结果 |
| --- | --- | ---: | ---: | ---: | --- |
| `new-arrivals-tight-n50-r4--a2--adaptiveV9` | V8 | D3 | 40 项 | 9 / 3 | MILP 响应 204.142 ms 到达，迟到接收拒绝 |
| `new-arrivals-tight-n50-r4--a3--adaptiveV9` | V7、V8 | D3 | 40 项 | 9 / 3 | MILP 响应 203.667 ms 到达，迟到接收拒绝 |
| `batch-release-tight-n50-r1--a2--adaptiveV9` | V7 | D7 | 79 项 | 9 / 4 | MILP 及时到达；最终选择 200.039 ms，拒绝 |

运输次数依据原缓存的提箱和还箱日期独立计数，同日提还按两次计算。三个缓存都确实违反了失败日的公开运输容量，不能继续直接执行。

### 两次 D3：迟到响应、原候选日期缺失

a2 的构造器尝试 16 次，没有形成完整已审核候选。MILP 请求剩余时间为 185.949 ms，原生内部时限 179 ms，调用墙钟 195.041 ms；响应在外层调用开始后的 204.142 ms 才到达。a3 同样没有构造候选，MILP 请求 186.335 ms、内部时限 180 ms、调用墙钟 194.954 ms；外层接收为 203.667 ms。

两次记录的 `outcome` 均为 `rejected_late_receipt`，`acceptedAtMs` 为 null。gate 在迟到接收处结束，没有复制保存完整日期。因此：

- 可以确认失败的直接在线机制是没有在外层截止前接纳有效候选。
- 原阶段记录 `solverStatus=2`、`status=feasible`，仅是 GLPK 报告；缺少日期时不能独立复核该原始迟到计划的物理和费用正确性。
- 不能说内部 `tmlim` 等于全调用墙钟，也不能把更大的内部时限当作已验证修复。
- 这不是父进程 5 秒超时。原完整失败历史分别在约 453.407/460.862 ms 被父进程收到并接受为已知失败结果。

### D7：已审核有效，但最终选择迟到

原始 gate 保存了该 50 箱候选的全部日期和新增两费 3,010,800 KRW：

| 阶段 | 相对外层调用开始的时刻 |
| --- | ---: |
| 实际收到 MILP 候选 | 199.107 ms |
| 隔离复制完成 | 199.252 ms |
| 物理、执行锁及费用审核完成 | 199.932 ms |
| 最终选择完成 | 200.039 ms |
| 正式接纳 | null |

独立 Python ledger 重新验证该日期集合的期限、连续卸货、逐日运输和堆存、过去锁及两费，全部通过，费用与原记录一致。原 `rejected_late_selection` 符合 200 ms 接纳规则；不能为了改善完成数把这 0.039 ms 迟到追认为成功。

这项证据排除了“所有原候选均物理无效”和“该当前观察加原执行前缀无解”的解释。但它不证明若提前接纳此计划，后续实际冲击下的完整 episode 必定完成。

## 初始路径是否相同

报告保留首次有差异的**已接受完整日期集合**、其 canonical SHA，以及在失败日前真实执行是否已经分歧。

| 比较 | 首次接受日期分歧 | 变化箱数 | 到 V9 失败前物理前缀是否一致 | 基准失败日计划能否直接用于 V9 原前缀 |
| --- | ---: | ---: | --- | --- |
| new-arrivals a2，V9 vs V8 | D0 | 43 | 否，D0 已分歧 | 否，会把 V9 尚未执行的提箱放到过去 |
| new-arrivals a3，V9 vs V8 | D0 | 43 | 否，D0 已分歧 | 否，同上 |
| new-arrivals a3，V9 vs V7 | D0 | 43 | 否，D0 已分歧 | 否，同上 |
| batch-release a2，V9 vs V7 | D5 | 2 | 是，到 D7 之前一致 | 是，独立当前快照与原锁审核通过 |

因此，两次 new-arrivals 的基准完整成功本身，不能替代 V9 原物理前缀下的可行性证明。batch-release 则有更强的同前缀证据：V7 的 D7 计划也能通过 V9 当日快照和原锁审核。完整路径实验与受控同前缀恢复实验仍需分开解释。

## 额外离线原生核验

经 root 确认，仅对这三个失败 episode 的“当前公开观察 + 原执行锁”请求旧独立 HiGHS 服务，每个请求声明 2,000 ms。两次 new-arrivals 重建出的快照及前缀完全相同，identity SHA 相同，复用同一个求解证据；实际只调用两个不同模型。

| 模型 | 声明离线调用预算 | 父进程实际接收耗时 | 原生状态 | 独立审核新增两费 |
| --- | ---: | ---: | --- | ---: |
| new-arrivals D3、原 40 项锁 | 2,000 ms | 27.942 ms | optimal，有完整 incumbent | 0 KRW |
| batch-release D7、原 79 项锁 | 2,000 ms | 14.485 ms | optimal，有完整 incumbent | 3,010,800 KRW |

原生服务启动另耗 230.539 ms，单独记录。该服务常驻后的离线调用实际耗时**不是原浏览器/GLPK 在线方法的耗时，也不是新的在线基准成绩**。不能因为本次离线在较短时间内完成就宣称替换引擎后必定及时成功；模型、初始化、跨层复制、审核与后续路径均不同。

原始 JSONL 请求、响应、ready 及每条 SHA 保存于 `artifacts/v9-loss-diagnosis-first/`，同时完整嵌入机器可读报告。请求只含重建的公开 scenario、原 fixedEvents、minEventDay、目标和离线 deadline。报告另外列出真实 model/solve/audit 耗时、原生证明状态、当前模型 scope 和逐箱第二套 Python 复价。

两个 incumbent 均经独立 ledger 检查完整箱覆盖、连续卸货、容量、TEU、半开堆存、原锁，以及每行和汇总两费；目标与独立复算一致。因此这两个当前观察模型均有解。本次没有原生无解或未知结论。今后若同类诊断只返回 timeout 且无 incumbent，应保留未知，不能改写成无解。

## 可以据此推进的修复假设

本报告支持把跨层剩余预算和最终接纳空间作为开发重点：内部求解结束并不代表外层已完成复制、重算、审核和选择。若开发新的求解与稳定性机制，应在相同总日预算内明确预留这些阶段，并检验最坏分支，而非给每一层各自增加预算。

new-arrivals 还显示早期计划的物理路径已不同，不能只分析 D3 调用就宣称找到了全部因果来源。若研究初始方案或稳定性选择，应固定对比前缀及观察，检查其对未来资源压力的影响，并保留未知解释。

以上均为开发假设，不是修复效果。任何新方法或参数必须先在开发资料上完成，再重新冻结方法、预算和分析规则，使用未看过的新留出场景验证。原 V9 的四个比较损失与三个失败 episode 保持原判。

## 只读复核

```sh
python3 scripts/diagnose-v9-losses.py --verify data/v9-loss-diagnosis.json
```

此命令重新绑定原档、重建公开快照及过去锁、核对首次日期分歧、原 gate 记录和额外原生 incumbent 的独立费用/资源证明；不运行新求解器，不重放在线策略。首次生成命令使用独占输出，拒绝覆盖已存在报告或原生诊断目录。
