# V10 压力完成损失：同费保留与未来恢复性的取舍

这是 V10 首次正式实验之后的只读开发诊断。原始索引 SHA-256 为 `33d07f60afb4b4248682badc631512a54070cca22fd106c7dd5062d4669bf9c2`。本次没有新求解、在线重跑、方法变更或新留出实验，也不替换原始完成结果。

机器可读证据见 [v10-loss-diagnosis.json](../data/v10-loss-diagnosis.json)。它逐项绑定原输入、V10/native 六份 episode、冻结实现及索引 SHA，保留首次日期分歧、公开快照、物理锁、原始 native 证明和选择时刻，以及一份独立 Python 重算的容量必要条件证明。诊断过程代码完整嵌在 JSON 中，没有修改方法或冻结源码。

## 先保留全部损失，再解释净改善

V10 对原生 HiGHS 在同分布完成 156/216 对 153/216，配对完成增益/损失为 3/0；压力面板为 132/216 对 120/216，增益/损失为 15/3。压力净增加 12 次完成，仍然有 3 次真实完成损失。

| V10 对照对象 | 同分布增益 / 损失 | 压力增益 / 损失 |
| --- | ---: | ---: |
| 原生 HiGHS | 3 / 0 | 15 / 3 |
| V9 | 26 / 15 | 36 / 12 |
| V7 | 27 / 15 | 37 / 12 |
| 稳定保留 V5 | 42 / 8 | 54 / 3 |

这些是相同场景、相同重复下的完成增益和损失，不能由净值抵消成“零退步”。预声明默认门槛要求对每个旧基准均无完成损失，因此本轮未通过默认推荐门槛。

## 三次损失只有一个独立业务场景

全部 native 完成损失都来自：

`v10-stress-new-arrivals-tight-n24-r3`

算法/时钟重复为 a1、a2、a3，种子 49011、49023、49039；它们不是三个新的独立业务案例。三次重建出的失败日公开观察与物理前缀相同，模型 identity SHA 相同。原生内部 RNG 固定为 0，也不能把三个 repeat 解释成三个不同原生随机算法。

| 重复 | 失败日 | native 到外层的时刻 | 整次日调用 | 父进程完整失败结果接收/审核耗时 |
| --- | ---: | ---: | ---: | ---: |
| a1 | D5 | 4.534 ms | 4.706 ms | 358.405 ms |
| a2 | D5 | 4.542 ms | 4.765 ms | 346.080 ms |
| a3 | D5 | 4.310 ms | 4.501 ms | 345.421 ms |

三次均是缓存失效后，native 在远早于 200 ms 的时刻返回 `status=infeasible`、`solverStatus=2`、`provenInfeasible=true`、`hasIncumbent=false`。原 gate 为 `no_incumbent`；原生和外层均无日调用超时，父进程也未触及 5 秒上限。这与 V9 的迟到候选机制不同。

## 无需求解器的独立不可行性证明

独立 Python ledger 从原始逐日执行事件重建 D5 前的 24 项物理锁，再核对原 observationHash 和 D5 公开仓库容量。原缓存的仓库审核失败、过去锁审核通过；不能继续执行缓存。

两个箱给出严格的 D5 仓库需求下界：

| 箱（共同前缀同上） | 原输入与已执行事实 | 任意合法恢复计划在 D5 的最低仓库占用 |
| --- | --- | ---: |
| C017 | 需连续卸货 2 天，已在 D4 实际开始卸货并形成物理锁 | D4–D5 连续占用，因此 D5 必须为 1 |
| C010 | 需卸货 1 天，截止 D5；D4 结束仍未提箱/开始卸货 | 未执行事件不能移到过去，D5 时最早卸货日为 D5、最晚也为 D5，因此必须为 1 |

D5 公开仓库容量为 1。故任何符合原历史和期限的计划，都有：

`最低仓库需求 1 + 1 = 2 > 当日已知容量 1`

这是一条当前公开观察与原物理前缀下的必要条件矛盾，不需要使用未来容量、JavaScript 模型或额外求解。JSON 中保留两个箱的原输入、锁、合法卸货日域和逐项来源，并在三次重复中分别重算。它独立支持原 native 的该层不可行性结论，避免仅凭“没有 incumbent”就判定无解。

证明范围仅是**V10 已经执行到 D5 的这条物理前缀**。它不表示从 D0 开始不可行、不表示 native 走过的另一条前缀不可行，也不表示现实中没有加仓位等菜单外补救。

## 原生基准为什么能完成：更早已走不同路径

V10 与原生基准在 D0 的接受日期相同；D1 首次分歧为 21 箱、43 项事件日期。真实执行也从 D1 起不同，不能把基准在另一条历史下完成，直接当成 V10 原锁下仍可恢复的证明。JSON 保留该首次完整日期对、canonical SHA 及失败日基准方案在 V10 前缀上的独立检查。

V10 的选择轨迹为：D0 初始化、D1 同费保留、D2/D3 缓存失效后替换、D4 再次同费保留、D5 当前前缀无解。

D4 的记录展示了具体取舍：

- 缓存与原生 proposal 的当前两费均为零。
- proposal 将改变 29 项待执行日期，V10 按预声明规则保留同费缓存。
- C017 在保留缓存中为 D4 开始卸货，在被拒绝的同费 proposal 中为 D8。
- 两个 D4 端点均通过当日公开观察、历史锁与费用的独立审核；D5 的未来减容当时尚未公告。

D4 选择保留缓存后，C017 在 D4 实际开始连续卸货，形成 D5 无法回退的仓库占用。这说明“当前同费且改期更少”可能与后续容量冲击下的可恢复性发生冲突；没有现有证据保证两者同时改善。

本诊断**没有**受控重放“只在 D4 换成 proposal”的路径，因而不能声称换一次计划就必定完成。更早的 D1 已经分歧，D4 以后的其它约束和执行也可能变化。必要的下一步是明确控制前缀和信息的开发实验，再重新冻结新方法并使用新留出验证，不能事后改判首轮结果。

## 费用与改期结论的边界

V10 对原生的共同及时完成配对中，改期总数确实减少：

| 面板 | 共同完成场景 / episode | 原生改期 / V10 改期 | 新增两费节省 | 95% 场景聚类区间 |
| --- | ---: | ---: | ---: | --- |
| 同分布 | 51 / 153 | 53,667 / 12,117 | −0.020% | [−0.107%, 0.030%] |
| 压力 | 39 / 117 | 45,972 / 17,625 | −0.285% | [−1.063%, 0.069%] |

总两费的区间也跨零：同分布 [−0.063%, 0.018%]，压力 [−0.628%, 0.042%]。负节省表示费用上升。可以报告减少改期及其条件费用结果；不能宣称稳定费用优势、全路径不退步或已经可以默认替换所有旧基准。压力面板还存在上述 native 完成损失，因此不满足预声明的“零 native 完成损失”稳定性声明条件。

所有费用和改期比较都条件于各自共同完成集合，不能跨不同配对分母排名。此次诊断解释的是合成每日原子模型中的稳定性/恢复性取舍，不构成真实业务节省、资源采购已执行或竞赛名次保证。
