# V5 第二实现只读复核

`scripts/review-v5.py` 是纯 Python 标准库的独立账本复核程序。它不运行求解器，不导入 JavaScript 引擎、费用函数、滚动规划器、V4 reviewer 或 HiGHS 证书脚本；也不修改实验档案。它在正式结果完整归档后读取冻结协议、静态结果、滚动结果及两份源码快照，重新计算可核验的费用、资源、物理执行和汇总口径。

```sh
python scripts/review-v5.py
node --test tests/review-v5.test.mjs
```

命令将 JSON 复核结果写到标准输出，成功退出 0；输入缺失、实验尚未完成或任何矛盾退出 1，并保留具体错误。不完整数据不会生成成功复核。归档结果由外部工作流保存 stdout；脚本本身不会覆盖 `data/`。审核计算是额外验证工作，不计入算法竞赛公平预算。

## 冻结输入和样本口径

生产模式固定协议原始字节 SHA-256：`7cfee99b5522236c3fd70a13b4fcbf11e2273d0c0cd3dd887465608c1f1c2109`。静态和滚动档案必须绑定同一哈希并保留相应完整协议内容；36 个主案例、24 个滚动案例必须按声明顺序全部出现，方法分别为 3 个和 2 个。主案例种子及滚动种子分别唯一。生成规则由 Python 重新实现，只在完整结果已经存在后重建声明情景，核对全部原始订单和参数；审核开发及单元测试不会生成或查看新种子情景。

六个 3 秒控制必须保留声明的 `referenceCaseId`，其整个 scenario 必须与对应主案例完全相同，包括原箱号、原情景 ID、日期、费用参数和容量。控制仅改变方法预算和输出分组标签。它们是同一组订单的重复预算，不是六个额外独立样本，不能混入 1 秒主实验的分母。程序分别重算两个汇总，检查 1,000/3,000 ms 预算及三方法轮换顺序。

两份 `vendor/experiments/v5-first-run-source` 和 `v5-rolling-first-run-source` 快照通过各自 manifest 和实验 `implementationHashes` 核对。报告同时列出当前源码哈希是否仍与首轮相同；当前代码后续变化不能改变首轮结果的源码绑定。协议哈希或源码快照匹配只说明所保留文件彼此一致，不提供外部时间戳或第三方预注册。

## 逐箱费用与完整方案

费用用 Python 日期和首尔 UTC+09:00 日历独立重算：08:00 前卸船当天开始存储，08:00 起翌日开始；提箱日计入 PNC，还箱日计入 D&D。默认 PNC 最高档追溯全部超免期天数，默认 D&D 按披露的累加假设。20/40 英尺分别计价，并重新计算规划前累计费用、总费用与增量费用。假设覆盖也可审计，但 V5 主实验采用冻结默认整数费率。

每箱核对尺寸、三个事件整数日、释放/先后/截止日、卸货持续天数和全部费用，再核对完整汇总。每日运输分别计提箱及还箱两次事件；卸货从开始到结束每天占槽；场地按 `[pickup,return)` 计跨日库存，支持按箱或 TEU 和逐日容量数组。记录有完整 rows 才能进入比较；任何失败、部分计划或未完成滚动 episode 的完整费用必须 null，不能用 0 或部分费用代替。

输出数字比较的绝对容差为 `1e−6`。本程序不求解最优值、不颁发最优证明，不把浮点容差内相等解释为精确数学最优。静态 `proven_optimal` 只是核对被归档的及时求解证明标签，没有独立重证；原生 HiGHS 校验若存在，仍使用独立 trip 模型和它自身披露的整数/数值口径。

可选 `data/certificate-v5.json` 必须绑定 `data/certificate-input-v5.json` 的原始字节 SHA-256；flatten 输入的 `originArchiveSha256` 和证书 `evidenceBindings` 再绑定原始 `benchmark-v5.json`。审核逐个比对 flatten 中的 36 个主案例和 6 个同输入控制的全部 scenario、policies 与原档案，检查 42 个证书案例顺序及每种方法完整覆盖，不能用相同 ID 配上不同输入。`evidenceBindings` 的协议哈希、两组案例 ID、36/6 分类计数、独立证书实现和 V5 wrapper 源码哈希也分别核对。42 是原生验证记录数；其中 6 个控制仍不是新增独立样本。证书缺失时明确报告 `not_provided`，不补最优结论；存在时其 omission、audit 费用、证书状态汇总及浮点标签均须一致。

## 因果信息与冻结历史

滚动两方法共享每个案例的 nominal scenario 和实际 shocks。实际容量由声明 shock 的揭示日、减量和私有持续时间重新生成。V5 主事件禁止 `announcedDuration`。每个决策日只把实际过去/当前容量放入观察，未揭示未来仍取 nominal；每日观察及其 checksum 根据这个信息集重新建立，不使用实际未来替换它。公开 observation 的 announcements 不能包含私有 duration。

每个接受的每日计划重新检查完整覆盖和当前观察下的全部硬约束；已执行 pickup/unloadStart/return 的日期必须与冻结历史完全相同，未执行事件不得放回过去。当天物理事件必须恰好与计划一致，不允许遗漏、重复、追加或失败后执行。持续卸货的资源占用继续核对。最终 rows 必须与逐日执行后的全部冻结日期相同。

待执行日期变化按相邻两个接受计划逐事件重新计数，已执行事件不计变化。程序核对每次 revisions 的具体箱号/事件/前后日期、累计值、状态轨迹与最终汇总。费用只在双方法均完成的同一 episode 上配对；所有失败、失去/新增完成案例、初始计划不同案例均完整保留。

## 稳定策略求解次数

`plannerTrace` 逐日保留返回元数据和 `callWallMs`，`plannerStats` 保存最后累计计数。每日重排必须每个决策日调用同一个 solver；稳定策略则独立检查上一个完整日期计划在当前观察与锁定历史下是否仍可行。仍可行就必须 `retained_plan`，日期不变、solverCalls 不增长、reusedPlans 加一；失效才允许 `solver_replan`，第一次为 `solver_initial`。该规则在审核中重新判定，而不只相信 `cacheAudit.valid` 标签。

审核重算每次和总 decisionCalls、solverCalls、reusedPlans、replannedDueToInvalid、planningWallMs，并核对两方法全案例和完成配对子集的计数。两方法有相同单次 solver 限时，但 episode 总调用数、总计算量不同，不能称总 CPU 预算相同。独立报告也提供配对增量费用，补充归档的总费用和日期变化指标；不会用单一复合得分掩盖完成失败或更高费用。

## 单元测试与范围

`tests/review-v5.test.mjs` 只用手工一箱情景及手算费用，没有调用引擎、生成器或求解器。它检查正常只读复核、档案缺失/未完成、逐箱篡改、失败零费用、控制输入更换、配对分母错误、未来信息泄漏、历史日期变化、求解次数虚报、违反稳定触发规则、迟到最优证明、协议/源码篡改、诚实失败的 null 费用和零配对分母，以及原生验证两层哈希、控制覆盖和内容绑定。测试必须显式 `--fixture --expected-protocol-hash`；报告标为 fixture，不能冒充比赛实验。

这项复核支持内部第二实现一致性。它不能证明线上真实节省、合同解释获承运人认可、部署时可用的日内时窗、真实订单总体、方法在所有未观察实例上的优越性、先进文献算法的完整复现或比赛名次。所有订单、容量和 shocks 是合成情景；声明其来源和失败边界属于可评审证据的一部分。
