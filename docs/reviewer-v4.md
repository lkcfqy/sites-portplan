## 二、已发现并修正的错误

### 1. 微小浮点费用被误称严格最优

构造合法输入：H=4、start=`2026-10-12`、truck=2、warehouse=1、staging=1，PNC 倍率 `1e-12`、D&D 倍率 1，目标 `storageOnly`。A20 卸船 `2026-10-04T07:00:00+09:00`，B40 卸船 `2026-09-27T07:00:00+09:00`；二者 release=0、unloadDays=1、due=2。

修正前，GLPK 次级求解给 A20 `(1,1,2)`、B40 `(0,0,1)`，主目标 `2.093e-7`，却标 `optimal` 和 `tieBreakStatus=optimal`。存在合法 A20 `(0,0,1)`、B40 `(1,1,2)`，主目标 `2.002e-7`，严格更好。禁用词典序的原求解也可能在微小目标下报数值最优而给更差候选。问题不在冻结协议默认整数费用，而在公开 API 的合法浮点参数和 `primary±1e-6` 次级放松。

现修正为：GLPK 的非安全整数主目标不发布 `proven_optimal`，保留原 solverStatus，同时公开 `feasible / solver_optimal_with_numeric_tolerance`；不进行严格词典序认证。安全整数主目标的次级固定改为 `GLP_FX` 等式；第二目标非安全整数时不称严格次级最优。`tests/numeric-v4.test.mjs` 保留该完整反例。

原 Python 审计的最小 `1e-6` 金额容差，也会把上述较差候选误标 `verified_optimal`。现非安全整数主目标只报告 `bounds_consistent_with_numeric_tolerance`；原生求解器的数值最优与严格证书分开。金额和 bound 容差写入证书。极小费率不是实际港口费率，但接口允许它就必须保持状态诚实。

### 2. 外部初解的金额不能成为优化依据

日期搜索原先仅检查初解日期/容量，随后信任行内金额；可行日期配上篡改的 0 或负费用会污染 standalone 搜索结果。首次同预算实验用的是引擎自己的未篡改初解，且 IPC 检查点经过独立费用检查，因此其原始结果没有依赖虚假初解费用。

当前实现先验证箱号、完整性及整数日范围，再用 `rowFor` 按权威 scenario 与提议日期重建费用；无穷日、未知箱、重复箱与不完整初解不进入计价循环。安全预处理本来就重算初解金额，未信任外部 totalCost。修复后的搜索可能改变时限内迭代数，故首次实验记录保留不被覆盖；准确源码在快照中。

### 3. 硬截止下的可行检查点须有一致语义

合法检查点可以在硬截止后保留完整可行 rows，status 为 `hard_time_limit`，其最优性必须降格，费用仍可核验。原生审计已允许这种完整候选，而非把它当作“部分计划”或将档案改写成成功求解。

研究页面曾把所有 `hard_time_limit` 都译为“无完整解”，与有完整 rows、费用和配对比较的检查点矛盾。现 formatter 根据 `retainedCheckpoint` 和 rows 显示“硬限时 · 保留完整可行解”；真正无解结果费用为 null。保留检查点不增加 GLPK 成功/最优计数。

### 4. 场景切换必须使旧 worker 回包失效

场景切换原先终止 worker，却未增加 job 版本；代码层面存在已排队旧消息覆盖新场景或访问已置 null worker 的可能。现切场景/停止均使 job 失效，消息与错误回调同时核对 job 和 activeWorker 身份。该项为代码审阅发现并修正，没有将其说成已观察到的浏览器事故。

## 三、安全预处理与最优状态的逻辑

每个全局完整可行解中，每箱三元组都单独满足自身先后、期限与其对资源的最低需求。因此各箱独立最低费用之和是下界；固定一个事件后的该箱最低费用，加其他箱独立最低费用，也是条件下界。只有条件下界超过已审计完整可行上界时才裁去事件。裁去的是不能改进该上界的选择，不能称为求解器 warm start。

已审阅以下保护：

- 上界来源逐箱重新计价，并通过完整资源/日期检查；无效或部分初解不形成 cutoff。
- 若一个事件不属于任何单箱合法三元组，可删除；若一箱连单独可行三元组都没有，可推出模型无解。
- cutoff 的浮点保护容差不用于声明达到下界。解析最优证书需要安全整数费用系数/和值及逐箱实际达到 minima。
- 解析证书只证明当前主目标。要求第二目标时不会绕过次级求解；预处理保留主目标最优集合。
- rolling fixedEvents / minEventDay 存在时，当前预处理明确禁用，防止未经核对地混用执行冻结与独立 minima。

这套推理支持“在所述模型中安全删域/解析下界证书”，不能从 18 例推广为普遍加速。六个解析证书全部来自零费用新到港场景；证明是非负下界已达到，**不是额外节省**。

## 四、同预算实际结果限制了算法优越性

父时钟从 fork 前到完整审计结果收到，共同限时 1,000 ms；迟到消息不被接纳，OS 定时/退出开销单列。仅一个方法子进程运行，case 内顺序轮换。归档全部 finalReceivedMs 均在预算内；被杀后保留的及时检查点均无最优证明。CPU 时限、墙钟、冷启动和浏览器运行不是同一个量，不能把这里的 Node 冷启动成绩说成用户浏览器性能。

关键反例保持公开：

- `v4-aged-backlog-balanced-n50`：原始 MILP 12,014,450，组合硬截止保留 13,921,500，贵 1,907,050 KRW。组合初始化占用时间并未换来普遍成本优势。

- 日期搜索相对排列仍有 1,300 与 9,100 KRW 两例增费；更丰富邻域不保证有限预算下每例更优。
- 100 箱六个场景，完整可行数为排列 3、日期搜索 3、原始 MILP 2、组合 3。不能声称 100 箱已有可靠普适性能。
- 所有方法在 `v4-aged-backlog-tight-n50` 都未交付完整解，但额外原生证书能求得最优 24,274,900。没有交付解不是模型不可行。

当前是一格一个 seed 的探索性矩阵，保留负结果且未替换场景。这没有企业订单分布、频率或统计代表性，不报告一般成功率/客户节省置信区间。改动 dispatcher、初始化份额或扩大预算后应另冻结协议，不覆盖这次不利结果。

## 五、因果执行结果支持恢复能力，不支持降费

这里的因果含义是“只用当时信息”，不是从观测数据识别真实业务因果效应。订单全部初始已知；未来容量冲击及未宣布持续期不进入 planner 输入。模型保留 p/u/r 已执行日期，已开始卸货仍按其已知固定工期占仓，不允许重启动来避开闭仓。历史容量保留已经观测的值，未来只用名义或明确已宣布预测；完成后的公开 usage 截断到实际执行结束日，避免把未发生未来容量带入结果展示。

| 策略 | 完整执行 / 12 | 失败 | 待执行事件改日期次数 |
|---|---:|---:|---:|
| 初始静态计划 | 5 | 7 | 0 |
| 因果每日重排 | 11 | 1 | 316 |
| 全知参考 | 12 | 0 | 0 |

有 6 个静态失败场景由滚动完成。只有 5 个双方完整执行可配对，终态总两费都是 873,600 KRW，差为 0；不能把恢复成功描述成省费。静态失败场景没有完整费用可与滚动方案相减。

`rolling-new-arrivals-n12-r1` 在第 7 日因已执行承诺下剩余模型无解而失败；全知参考可行，不推翻冻结历史后的不可恢复结论。必须让该失败与恢复案例同样可见。全知方案是额外信息参考，不是在线策略成绩。

每次求解限时同为 0.2 秒，但滚动有更多调用与日期修改，**总预算不相同**。316 次是待执行事件日期变化总数，不是箱数、司机改单次数、独立扰动数或实测运营损失。未知新订单、放行延期、随机卸货时长、车辆路径和预约窗口未在本轮完成，不能因已固定卸货开始日便宣称完整实时调度。

## 六、可提交的窄结论与后续验证

可说：公开费率编码和日级执行状态可核验；更直接的日期邻域补强了内部基准；首次端到端对照保留了超时、零收益和负收益；已实现只看当时容量信息、冻结执行动作的滚动模拟；独立 Python trip-column 模型对全部 18 例和 53 个候选未发现矛盾。

不能说：普遍优于已有先进算法、联合 D&D/滚动调度首创、预处理普遍降费、100 箱稳定解决、企业实测节省、现场可执行保证、用户本人已完成核验或可预测获得第一。文献先例与本轮读取深度见 [研究路线](research-roadmap-v4.md)，实际 AI 研发记录见 [贡献台账](contribution-log-v4.md)。

局部“晚一天仓储费暴露”若加入界面，应保持局部费用差标签；尚未完成同 snapshot 下禁止今日动作后的全局反事实求解与界，不能把它说成全局推荐原因或可认证延期代价。

下一阶段优先验证当前代码在独立冻结 seed 上的 budget dispatcher 和初始化份额，再扩未知订单/工期状态；继续保留无收益、无解、恢复失败与费率解释变化。公开研究可以自主推进。源代码 ZIP、生产构建、浏览器交互和正式报名/提交状态由相应实际检查记录负责，本文不以静态代码阅读替代这些操作验收。
