# V8：执行锁下的保留、费用小修与失效重建

`src/adaptive-planner-v8.js` 是当前日级、全订单已知模型上的新策略实现。它复用 V7 完整种子的费用修整，以及 V6/V7 的执行锁构造和剩余预算 MILP，不修改旧版本源码和首次实验。这里描述可检查的机制和手工测试，**没有报告新留出性能、真实企业节省、算法首创、最优性或比赛排名**。

问题收紧为：已有计划后，什么时候继续保留，什么时候花预算小修，什么时候因当日信息变化必须重建。初始化单列。V7 未完成案例的独立离线诊断由其他工作包负责；不能把 D0 初始化找到解包装成相同执行历史后的恢复成功。

## API 与实例边界

```js
import {createAdaptivePlanner} from './src/adaptive-planner-v8.js';

const planner = createAdaptivePlanner({timeBudgetMs: 200});
const candidate = await planner(observedScenario, {
  objectiveMode: 'joint',
  minEventDay: today,
  fixedEvents: executedDates,
});
```

每个连续 episode 建立一个新 factory；同一实例的调用必须串行。传入不同业务身份、订单字段、操作规则、规划起点/长度，或倒退决策日时，旧日期缓存失效重置，不能从另一 episode 直接保留。费率和观测容量可以改变；缓存只保存三个日期，必须用本次费率重新计价并再次审计。输入、工厂初始日期、回调参数、输出和内部缓存彼此复制隔离。

可选配置 `initialDates: [{id,pickupDay,unloadDay,returnDay}, ...]` 用于已知共同执行前缀的对照试验，只在 factory 第一次调用消费。必须包含所有已知箱，并通过本次容量、费用、执行锁和最小决策日审计。它不是优化器生成的初始化成果。初始日期不合法则记录拒绝并尝试重建，不将不完整参考的日期变化数补为 0。

`now`、`solver`、`seedConstructor` 可以在配置中注入；后两者沿用 V7 的接口。另可注入 `polish(snapshot, completeSeed, options)`，默认 `polishCompletePlan`，用于检查晚返回、错误及非法候选等边界。注入回调收到隔离副本，其结果仍按原始本次快照重新计价、审核；回调自称的费用、最优性和可行性不能绕过审核。

调用预算优先级为：本次 `timeBudgetMs`、本次 `timeLimitSeconds × 1000`、工厂 `timeBudgetMs`、工厂 `timeLimitSeconds × 1000`、默认 200 ms。工厂参数在实例建立时固定；本次业务信息和锁放在调用 options 中，不通过配置保存执行历史。

## 当前可见信息

控制器读取传入快照里的订单、公开费率、历史/当天容量、未来名义容量和精确执行锁。执行锁日期必须严格早于 `minEventDay`；当天开始决策之前还没有当天已执行动作，D0 不接受任何执行锁。未来承诺预约不能伪装成过去动作。它没有未来实际容量或私有 shock API，也不猜测未知持续时间。未来两天的资源量均是**传入预测下的确定性代理**，不是失效概率、实测未来或鲁棒保证。

因果性依赖 `runRollingScenario` 的观察边界：模拟器持有真实未来，只交付当天可见快照。测试用两条未揭示未来不同而前缀相同的路径，核对早期决策与传入回调的信息一致。新出现订单、道路路线、预约窗、司机班次和日内资源顺序仍不在模型内。

## 三种动作

1. **初始化/重建。** 没有缓存时为 `initialize`；完整历史日期因当前容量或执行锁审计失效时为 `rebuild`。复用 `createCostRecoveryPlanner`，把外层剩余预算减去末端审计预留后传下去。每次重建使用全新的 V7 实例，日期缓存只由 V8 管理，避免旧的内部缓存跳过控制器判断。初始化没有“比上次少改日期”的有效参考；相关值为 null。
2. **保留。** 缓存经过本次完整审计及重新计价后，先成为可回退的 incumbent。没有超过固定阈值的乐观费用机会、变更额度为零、预算不足，或者小修不满足接受条件时，保留此 incumbent。
3. **小修。** 仅对已审计有效缓存调用现有 V7 单箱/双箱费用修整，不对无效缓存 polish。修整和外层选择共用本次剩余预算。返回候选须再次按原快照审计，并通过下述费用、改动及资源压力守门。

没有完整方案时返回 `status=no_feasible_schedule_found`、空 rows、null 完整费用、`optimality=not_proven`。V7 子问题声称 infeasible/optimal 不会自动升级为 V8 整体证明。没有放松交付期限、删除箱、修改已执行事件或给失败填造完整费用。

## 费用机会与日期变化

每箱在忽略所有共享容量时，取满足 release、执行锁、未执行事件不回到过去及先后约束的最早 p/u/r。当前已支持的费用函数随日期不下降，因此此独立日期费用之和是松弛下界。缓存增量费减去该下界，是**乐观费用改善上限**；它不是已找到的全局可行节省。计算耗尽预算时返回 `complete:false` 和 null 上限，不补成零机会。

另记录近两天计划提/还事件延后一天时的公开收费差。这是 `nearTermOneDayFeeExposureKRW`，只用于说明收费跳档；它不额外触发必定有益的重排，也不保证该延期满足容量、期限或规划末日。

日期变更只计算未执行的 p/u/r 字段：改变的事件个数、绝对移动日数、原定今天/明天的变更数。近期变更按权重 2、其余 1 的加权数仅作为诊断字段；当前选择和默认六次变更上限使用未加权事件个数，不把这个权重声称为真实改派成本。

两份及时完整候选为缓存 C 与 polish P。设 `Cmin = min(C.incrementalCost, P.incrementalCost)`，稳定性容忍线为 `Cmin × (1 + feeToleranceRatio)`。接受 P 必须全部满足：

- P 在同快照的增量费严格低于 C；等价于总两费严格降低，因为两者费用基数相同。
- 改变的未执行日期字段不多于 `maxChangedEvents`。
- 启用压力守门时，P 的各资源预测峰值利用率和满载日数均不增加。
- C 的费用已经高于稳定性容忍线；若两者费用接近，优先不改日期。
- 包括重新审计和选择在内的接受工作在本次外层 deadline 内完成。

`feeToleranceRatio` 是公开的稳定性偏好，不是经过企业核实的金钱成本。零最低费用的容忍线仍是零，不增设任意固定韩元底数。选择只在这两份找到的完整方案中进行，没有穷尽邻域或全局 Pareto 最优声明。初始化/失效重建仍采用原 V7 候选选择，不宣称已实现独立的稳定性目标 MILP。

## 资源压力守门

窗口为决策日后的 `d+1` 至 `d+lookaheadDays`，截于规划期末。今天的物理可行性已经由完整审计约束；这里只比较未来预测。每资源报告：

- 正容量日的峰值 `usage / suppliedCapacity`；
- 正容量日中完全用满的天数；
- 所有窗口日的最小绝对余量；
- 零容量日数。零容量不参与除法，不能生成 NaN 或 Infinity。

接受守门比较峰值与满载日数。它是可消融的保守启发式，可能拒绝真实可行、费用更低的方案；手工测试明确保留这种反例。它不证明未来任意冲击下可行，也没有优化资源利用率或预先知道冲击时长。

## 固定实现默认值与预算

| 参数 | 默认值 | 含义 |
|---|---:|---|
| `timeBudgetMs` | 200 | 整次 callable API 的合作式预算 |
| `feeToleranceRatio` | 0.005 | 缓存落在最低已找到费用上方 0.5% 内时偏好不动 |
| `maxChangedEvents` | 6 | 一次可选小修最多改变六个未执行日期字段 |
| `lookaheadDays` | 2 | 未来名义资源压力和局部费率暴露窗口 |
| `pressureGuard` | true | 不接受预测峰值或满载日数增加的小修 |
| `opportunityThresholdKRW` | 0 | 乐观费用机会必须严格为正才尝试小修 |
| `auditReserveMs` | 5 | 给外层候选审核/选择预留时间 |

这些是新实现明确声明的设计值，没有用 V8 新留出结果择优，尚未经过正式性能评价。V7 内部构造份额、重启和 polish 邻域仍可按原配置指定。为了不更改已冻结历史，默认不修订 V7 的算法和参数。

时钟从进入调用、复制输入之前开始，覆盖验证、缓存审核、费用机会、polish/恢复、再审计与选择。时钟必须返回有限毫秒。导入与 factory 构建发生在 callable API 建立前；完整冷 episode 比较仍应由父进程另设共同硬预算，不能把合作式 200 ms 当成绝对中断。

若缓存已经在本次预算内完整审核接受，后续阻塞/晚返回的小修不能替换它，允许回退到早先已接受的 incumbent，并如实报告 `deadlineOverrunMs`。如果首次当前快照审计本身已经超时，则没有本次及时 incumbent，返回失败。外层完整 episode 是否及时仍取决于父层终局接受，不能仅凭 `incumbentAcceptedBeforeDeadline` 宣称父层成功。

## 结果、核验与性能边界

标准候选的 `policy=adaptiveV8`，所有成功状态均为 `feasible`。`plannerMetadata` 包含：

- `action`: initialize / retain / polish / rebuild / failed；`strategyAction` 保存失败前尝试的分支。
- `decisionReason` 原因码和 `reason` 说明、缓存有效性和及时接受状态。
- `feeOpportunity`、`selection`、`dateChanges`、`pressureProxy`。
- `phaseWallMs`、`stages`、预算/overrun、incumbent 接受时刻；恢复时另存 `recoveryMetadata`。
- 本 factory 累计 decision/solver/constructor/polish/reuse/invalid-cache 计数。未提供完整参考的初始化改动数保持 null。

核验命令：`node --test tests/adaptive-v8.test.mjs`。手工测试包括独立完整日期域枚举/计费/资源 oracle、同快照成对小修、稳定性拒绝、压力拒绝反例、零容量、进行中卸货、精确历史锁、失效重建、晚返回保留、复制计时、回调篡改、费率重计、实例隔离、未知未来相同前缀、预算优先级和默认 V7/GLPK 小例集成。

这些测试验证实现机制，不表示新方法提高了完成率、降低了终局费用或减少了整条路径的改派。局部当前费用非增不能推出滚动路径全面占优。后续必须将初始化覆盖与共同前缀恢复分开，冻结新协议/输入/参数，纳入稳定保留、V7、固定触发及更强外部方法，保留全部失去完成、费用上升和未知证书结果。

不可行证明由独立离线诊断提供；知道全部未来的离线见证不进入在线输入。应急资源购买、额外容量定价或软化期限属于另一个明确标注假设的情景工具，本模块不自动加资源、编造价格或计入新的财务收益。
