# V15 开发声明：为完整原生候选预留交付时间

本轮只检验一个改动：在冻结 V12 的经济接纳、40ms 构造器、同费 M 比较及完整接纳审核不变的条件下，给原生请求固定提前 **10ms** 的绝对返回目标。整体合作预算仍为 **200ms**，原生目标为 190ms，Python 原审核预留仍为 2ms；接收、复制、费用、历史锁、资源及选择审核必须在原 200ms 内真实完成。190ms 是返回目标，不是硬时钟保证；195ms 才收到的完整候选若全审核及时仍可接纳，200ms 后审核完成的候选不能追认。

新方法为 `timelyHiGHSV15`，独立实现位于 `scripts/highs-planner-v15.mjs`。V12 为主经济骨架对照，V13 严格省费 M 守卫保留为负面对照；V1–V14 冻结源码、协议、首跑及负例均不改写。本轮不调 10ms 参数、不增加风险代理，也不以重新运行历史正式实验获得更好分数。

[protocol-development-v15.json](../data/protocol-development-v15.json) 声明 **4 个已见合成业务场景 × 原 3 个重复 × 3 个方法 = 36 个冷分支**。它不是新留出验证，不是 36 个业务样本，不计算置信区间。四案取自 V14 全部完成损失并集；每个 case 的全部原重复均纳入，即使该原重复本来完成也不删选。每个重复使用自己的原 V13 物理前缀及旧算法种子 79011 / 79023 / 79039，不按是否成功合并或择优选前缀。

每个分支从 D0 启动同一冻结模拟器，强制返回该重复归档的完整日期，再重新计价、审核、执行。逐日核对 day、公开观察、observationHash、完整决策、实际执行动作、物理状态、改期明细和累计改期这八项投影。归档日期没有重新被原生算法发现，前缀阶段新增规划/构造/原生请求均为零。首次真实规划日三方法收到相同的公开快照与历史执行锁，此后各自按真实选择继续到结束，未来事件只由模拟器在原揭示日公开。

**这是统一不导入历史私有缓存的 cold-cache 切片实验。** V12 没有历史缓存导入接口，本轮不改写其实现或使用假原生响应预热。三方法均从相同空私有缓存开始，原物理前缀仍真实保留。八条原损失记录的失败日缓存均失效，但不能由此说忽略缓存审核开销完全不影响原时钟，其他原重复也不被假定等价。因此本轮不能称为自然 D0 全路径速度、原 V13 历史时钟复现，或已证明对自然缓存轨迹的整体改善。

每支完整冷生命周期保留冻结 V12 父契约：冷进程/模块加载、原生 ready、回放、真实续日、终态双审、IPC、正常退出、ESRCH 进程组消失确认和父审核都须在同一 **5 秒** 内完成。每次真实决策仍为同一 200ms 合作预算、单原生线程、原生 RNG 0。未知历史不能写成零次执行，未接纳迟到候选和原始收据不能抹掉，失败费用保持 null。回放日同样要求在 200ms 内完成重建、审核和收据工作；任何失败不补跑或续跑。

唯一顺序写在协议 `jobs`：原重复 1、2、3 为外循环；每轮旋转首个 case，再按 caseIndex 与 repeat 旋转三方法先后；相同端点的三方法相邻，全部串行执行一次。只比较实际匹配且共同完成的终态费用和改期，逐端点同时保留未完成、失败日、公开输入、候选完整时刻及父生命周期；不能拿条件费用覆盖完成损失，不能把另一个前缀的成功计划当成当前锁下的恢复证明。
