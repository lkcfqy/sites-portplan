这是首次正式结果之后的只读诊断。原索引 SHA-256 为 `141ac68b0627e74ffa41f881078d9d73304263240e858d148c64e91562217646`。完整原始成绩、算法、协议、种子和候选截止均未修改；没有重新求解或新增样本。诊断涉及的场景从此属于已见开发证据，不能再次充当新留出。

机器可读证据为 [v12-loss-diagnosis.json](../data/v12-loss-diagnosis.json)，复算程序为 [diagnose-v12-losses.py](../scripts/diagnose-v12-losses.py)。JSON 保留全部负例完整 ID、输入及双方 raw SHA、失败日公开快照、实际执行锁、原生状态与时刻、逐箱域和独立必要条件。首次 [物理审核](../data/review-v12.json) 与 [统计审核](../data/bootstrap-review-v12.json) 均已通过，属于内部独立实现，不能当成第三方认证或竞赛成绩。

两个面板各含 72 个业务场景、三个算法/时钟重复，共 216 episode。V12 同分布完成 181/216，压力完成 120/216；原生 HiGHS 分别为 166/216、105/216。

| V12 对照 | 同分布增益 / 损失 | 压力增益 / 损失 |

| 原生 HiGHS | 19 / 4 | 18 / 3 |
| V10 | 13 / 1 | 9 / 3 |
| V11 | 13 / 1 | 9 / 0 |

这些是同场景、同重复的配对结果。预声明的默认替换门槛要求对各旧基准无完成损失，因此本轮未通过。开发集上的零损失没有延伸为正式零损失。

本诊断取五组对照损失的**并集**：同分布 5 episode / 3 个业务场景，压力 14 / 5，总计 19 / 8。一个负例可能同时输给多个基准，不能把各列相加作为独立失败数；三个重复也不是三个独立业务案例。它不是对全部 131 个 V12 失败的完整归因。

## 两个 D0 损失是不同的交付问题

`aged-backlog-tight-n50-r3` 的 a2 没有构造候选回调，构造阶段约 47.13ms；native 最后仍无 incumbent，日调用约 238.56ms。它是预算内候选覆盖/交付失败，不能称为物理无解。V7/V9 在同一个 D0 公开快照、空执行锁下的完整日期已用独立 Python 重新审核，确实提供可行见证。

`new-arrivals-tight-n100-r4` 的 a1 则已有完整构造候选：

| 原记录时刻 | 毫秒 |
| --- | ---: |
| 构造回调收到完整日期 | 39.456744 |
| 日期复制完成 | 39.753806 |
| 外层审核完成 | 41.840893 |
| 原构造子预算截止 | 40 |
| native incumbent 到达外层 | 228.523889 |
| native 日期与费用审核完成 | 234.475510 |
| 整次日调用 | 236.530400 |

构造候选收到时尚未越过 40ms，但审核完成后已越过该子限，被原规则以 `late_audit` 拒绝；native 也超过 200ms。独立 Python 确认这份未接受构造日期在原 D0 模型下可行。这个事实揭示了子预算划分与候选交付的取舍，**不允许事后把它改判为及时成功**，也不能保证换一种预算划分后整条 episode 就会完成。

## 十七个后续损失不能混成超时

19 个负例中，另外 17 个均在缓存失效后收到及时的原生 `infeasible`：D4 或 D6，到达外层约 12.53–36.96ms，远小于 200ms；原 `hasIncumbent=false`、`provenInfeasible=true`。没有父进程 5 秒截止导致的未知历史。日调用超出合作目标与五秒父截止是不同层次，D0 迟到也没有被改写成父超时。

独立复算只接受名义已知订单、截至失败日的已存公开观察/明确公告，以及更早真正执行的事件。未公告未来容量、冲击持续时长和对照方法的未来计划不进入必要条件计算；全部 19 个原 observationHash 均重新匹配。

对每个箱枚举符合 release、连续卸货、完成截止、还箱 lag、计划期和原执行锁的单箱日期域，暂时放松共享资源分配。逐箱对失败日占用取最小值后求和，任何真正联合可行续解都不能低于它。压力面板的 14 个负例均有上表的严格仓库矛盾，因此无需新求解即可证明**该条已执行前缀在当前公开模型下无解**。JSON 同时保留当前日及仓库区间能量条件，未将必要条件通过当成可行性证明。

同分布 `new-arrivals-tight-n24-r3` 的三个 D4 失败没有违反本次较弱的逐箱/仓库区间必要条件。这不推翻 native，也不证明可恢复；准确结论仍是“native 报告当前模型无解，尚缺本次结构独立的证书”。

所有 17 个后续负例中，完成的对照都已经走过不同的物理前缀。D4 三例从 D2 分歧；压力场景多数从 D0 分歧，native 的 `batch-release-tight-n50-r3` 从 D1、V10 的 `batch-release-tight-n100-r3` 从 D4 分歧。其当前日期套回 V12 原锁后均不能通过审核，不能拿对照完成当作 V12 原前缀仍可恢复的证据。

## 条件费用已经出现明确负面

费用比较仅在各自双方共同及时完成的集合内进行；失败路径没有完成费用，不能把它们填零。原生对照的结果如下，百分数表示“基线 − V12”的节省，负数表示 V12 更贵：

| 面板 / 条件分母 | 总两费节省及场景聚类 95% 区间 | 新增两费节省及区间 |
| --- | --- | --- |
| 同分布：55 场景 / 162 episode | −0.06630% [−0.22770%, 0.02359%] | −0.12003% [−0.39688%, 0.04367%] |
| 压力：34 场景 / 102 episode | −0.42382% [−1.44837%, −0.01131%] | −0.73405% [−2.35461%, −0.01999%] |

压力面板的两个费用区间均在负侧：这是该共同完成样本中的费用恶化，不能只说“尚无稳定节费”。34 个场景按节费符号分为 8 负、2 正、24 平，最坏单场景多 688,750 KRW。场景内匹配重复取均值后的费用和增加 1,239,200 KRW；对应原 episode 费用和增加 3,717,600 KRW。两种聚合分母不同，不能混写。

## 有限的下一步

1. **先补候选交付边界的开发验证。** 区分 40ms 构造搜索与完整审核需要的时间，在保持 200ms 全局预算下预声明审核预留或跨层接纳规则，保存全部回调、拒绝时刻和 native 剩余预算。需要与原规则消融；额外审核可能挤占求解时间，不能预先保证改善。50 箱无收件问题另算候选覆盖，不能都归因于 40ms 审核边界。
2. **补三个 D4 案例的独立结构证书。** 对原公开快照与原锁，用独立资源区间/模型诊断区分更强的不可行证明与证据不足。只做失败模型的离线诊断，不能改用对照的另一条历史或事后未来容量。
3. **对五个压力场景检查不可回退动作之前的选择。** 只比较当时已经实际产生、及时且通过原审核的端点，先做固定共同前缀分叉。检查费用优先、今天动作、次日必要负荷及其它资源之间的冲突，再决定是否值得增加更长区间约束；不得用已知 D6 实现值回填在线策略，或声称降低 M 就有恢复保证。

这些是下一阶段待验证事项，本轮没有实现或修复它们。任何新方法须另行冻结，并以新的未见样本检验完成损失、条件费用及改期；本次负例和原默认门槛失败必须继续保留。公开资料路线可以继续推进，当前结果不构成真实企业收益或比赛名次保证。
