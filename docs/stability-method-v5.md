# V5：保留仍可执行的计划

V4 的每日重优化允许改动所有尚未执行事件，即使前一日的完整计划在新信息下仍然可行。新的 V5 策略优先保持已通知的事件日期：**只在首次规划，或当前信息使已缓存完整计划不再有效时调用求解器**。这是稳定优先的启发式策略；本项目不声称该规则首创、全局费用最优或具有竞争比保证。

实现位于 `src/stable-planner-v5.js`，入口为 `createStablePlanner(configuration)`。返回的异步 `planner(scenario, options)` 可直接交给 V4 的 `runRollingScenario`。每个滚动实验创建独立实例，按日期串行调用；实例内的缓存及计数只属于该规划过程。

## 信息和执行范围

沿用 V4 的日初信息规则：所有合成订单在初始已知；未来未揭示容量使用名义预测，已明确公布的冲击持续时长才进入已知未来。V5 不读取完整冲击路径，不扩展为未知新订单、未知卸货工期、实时港口数据或日内运输路线。策略只接收 V4 已构造的当天 snapshot 及原始日索引。

`options.fixedEvents` 记录此前已经发生的提箱、卸货开始和还箱日期；`options.minEventDay` 禁止未执行事件被安排到过去。开始卸货后，其开始日锁定，持续占用卸货槽至原引擎定义的完成日。提箱与还箱各用一次运输；卸货区间包含起止日；箱位按 `pickupDay ≤ day < returnDay` 计。这些资源语义与 V4 相同。

## 每日决策规则

1. 克隆当前 snapshot 和执行约束，验证输入、日索引、锁日期和每日容量。
2. 缓存只保留各箱 `id/pickupDay/unloadDay/returnDay`，不缓存费用、完成日、尺寸或求解证书。
3. 使用当前订单、收费参数和缓存日期调用 `rowFor`，重新计算卸货完成日、逐箱收费与汇总费用。
4. 先检查所有日期为规划期内的有限整数，再执行 `auditSchedule` 和 `auditFrozenEvents`。
5. 两项审计均通过时，完整保留日期，返回 `status: "feasible"`、`optimality: "retained_plan_not_reoptimized"`。不继承前次最优、二级最优或下界证书。
6. 无缓存或缓存审计失败时，调用 `solveOptimized`，原样传递当前锁及最早事件日。求解结果先克隆，再以未被求解回调修改的 snapshot 双重审计，最后按真实输入重算费用。仅完整通过审计的日期进入缓存。
7. 求解失败或候选非法时，返回空完整排程及 null 费用。原缓存即使保留在闭包中，也不能未经当前审计重新使用。进行中卸货遇低于固定占用的容量时，允许明确失败，不能重新开始卸货消除占用。

工厂还校验规划过程身份：规划起点、期限、已知订单、操作规则或场景身份变化，及日期倒退，都会使旧缓存失效，避免新实验错误复用旧解。这只是缓存防线，不是新增订单处理方法。费用参数变化会按当前参数重新计费；只要原日期仍然有效，稳定规则仍然保留日期。

## 接口和可检查记录

```js
import {createStablePlanner} from './src/stable-planner-v5.js';
import {runRollingScenario} from './src/rolling-plan.js';

const planner = createStablePlanner({timeLimitSeconds:0.2});
const execution = await runRollingScenario(nominal, capacityEvents, {
  planner,
  timeLimitSeconds:0.2,
});
```

可在工厂或单次调用的 `solver` 字段注入回调；回调收到的内容只包含当前 snapshot 和求解选项，不含未来冲击。工厂的其他数据选项作为求解默认值，单次调用覆盖默认值；当前 `fixedEvents/minEventDay` 始终保留。返回值 `plannerMetadata` 含累计计数及本次来源：

| 字段 | 含义 |
| --- | --- |
| `decisionCalls` | 有效输入的规划调用次数 |
| `solverCalls` | 实际调用求解回调次数，异常和失败也计入 |
| `reusedPlans` | 当前双重审计通过、未调用求解器而保留日期的次数 |
| `replannedDueToInvalid` | 曾有缓存、但当前调用使其失效而重求解的次数，失败也计入 |
| `candidateSource` | `solver_initial`、`solver_replan` 或 `retained_plan` |
| `accepted` | 本次是否返回完整通过审计的方案 |
| `cacheStatus` | `absent`、`valid` 或 `invalid` |
| `cacheInvalidationReasons` | 当前失效原因，包括资源、冻结历史和未执行事件日期 |
| `cacheAudit` | 对已有缓存进行的资源/先后/日期及冻结历史审计；无缓存或规划身份已变时省略 |

计数在工厂实例的整个生命周期累计；切换规划身份不会清零计数。`cacheStatus` 描述本次调用开始时的缓存是否适用于当前信息，不表示调用结束后是否已有新缓存。新实验必须重新创建工厂实例，即使它与上一次具有相同场景字段和同一日索引；不要并行调用同一实例或用它跑多个并列实验。

计数描述求解策略，不能替代最终执行审计。V4 的 `revisionCount` 仍统计尚未执行事件的日期变更次数；保留一整份日期时，本次变更为 0。真正重排仍可能改变多个未来事件，不能声称所有冲击下均为零变更。

## 代价与评估要求

容量恢复或增加时，一份原先可行的计划可能已有更便宜的替代日期。V5 会保留原计划，因此可能比每日费用优化支付更多，也可能在后续未知冲击下更难或更容易完整执行。减少求解次数和日期变更并不证明费用、完成率或韧性同时改善。

V5 使用新的冻结留出种子比较 V4 每日重优化（`dailyReopt`）和 V5 保留可行计划（`stableRetain`）两种策略；静态原计划是 V4 历史对照，不属于 V5 的 24 个滚动案例。保持同一名义输入、已知订单、真实冲击、信息揭示规则、执行锁及每次求解限时；分别报告完整完成数、失败日与原因、完整执行费用、日期变更数、求解调用数和耗时。只在双方完整成功的同一情景上作费用配对，失败费用保持 null。初始计划应相同，或明确核验/报告初始解差异，避免限时求解或多解选择被误当作稳定规则效果。不同求解次数意味着总计算预算不同，不能声称等总 CPU 比较。

`tests/stable-v5.test.mjs` 使用求解 spy 检查不必要重求解被省略、资源/锁失效触发重排、未知未来前缀不变、收费和可变输入隔离、失败语义、进行中卸货占用以及正常 GLPK 接入。测试包含“容量恢复后更便宜方案可行，但仍保留旧计划”的反例，直接限制最优性声明。这些是实现验证，不是新留出实验的效果结论；V4 历史结果保持原样。
